프로젝트 2일차에는 작업 관리 방식을 Notion의 개인 To do에서 GitHub 이슈 중심으로 전환했다. 오전에는 바뀐 칸반보드 사용법을 공유하고 설정 문제를 해결했으며, 이후 각자 EDA를 진행했다. 마무리 회의에서는 팀원별로 발견한 데이터 이슈를 공유했고, 각도만 다른 알약 이미지를 같은 데이터로 볼 것인지를 두고 논의가 이어졌다.

## 1. 주요 일정

| 시간 | 활동 |
| --- | --- |
| 오전 10시 | 오전 회의: 작업 관리 방식 변경 공지 |
| 오전 회의 이후~오후 | 칸반보드 사용법 안내, 설정 문제 해결, 개인별 EDA |
| 오후 6시 | 일일 마무리 회의: EDA 결과 공유 및 쟁점 논의 |

## 2. 작업 관리 방식 전환: Notion To do에서 GitHub 이슈로

### 전환 배경

1일차에는 Notion 프로젝트 페이지의 To do로 할 일을 관리했고, Notion과 GitHub Projects 중 어떤 도구를 쓸지는 2일차로 넘겼다. 개인 To do는 각자의 할 일을 정리하는 데는 충분했다. 하지만 EDA 중에 발견한 중요한 사항을 팀 전체에 바로 알리기는 어려웠다.

### 변경된 관리 구조

2일차부터는 GitHub 이슈를 중심으로 작업을 관리하기로 했다. 기존 To do의 역할은 개인별 이슈 관리로 대체했고, 전체 일정은 Notion에 새로 정리했다.

| 구분 | 도구 | 역할 |
| --- | --- | --- |
| 전체 일정 | Notion | 프로젝트 전체 일정 관리 |
| 개인 작업 | GitHub 이슈, 칸반보드 | 담당 업무와 진행 상황 관리 |
| 중요 발견 사항 | GitHub 이슈, Discord 알림 | EDA 중 발견한 특이 사항을 팀 전체에 공유 |

특히 EDA에서 특이 사항을 발견하면 이슈로 등록해 모든 팀원에게 알림이 가도록 공지했다. EDA 초반이라 할 일을 미리 정해두지는 않았다. 정해진 할 일을 나눠 맡기보다, 발견한 문제를 이슈로 쌓아가며 공유하는 구조를 먼저 마련하는 데 의미를 두었다.

### 도입 과정에서의 어려움

오전 회의 이후 오후 회의 전까지 팀장은 바뀐 칸반보드 사용법을 안내하고 각종 설정 문제를 해결하는 데 많은 시간을 썼다. 팀원마다 이슈 도구와 설정에 익숙한 정도가 달라 설명과 문제 해결에 시간이 필요했다.

1일차의 공통 개발 환경과 마찬가지로, 도구를 정하는 것만으로는 팀이 같은 방식으로 일하게 되지 않았다. 팀원 모두가 도구의 사용 흐름을 이해하고 실제 작업에 적용할 수 있도록 돕는 과정이 함께 필요했다.

## 3. EDA 결과 공유

오후 6시 마무리 회의에서는 각자 진행한 EDA를 이슈 중심으로 발표했다. 발견한 이슈마다 당일 해결한 것, 다른 팀원에게 인계한 것, 장기적으로 다룰 것을 나눠 정리했다.

| 담당 | 발견한 이슈 | 후속 조치 |
| --- | --- | --- |
| 팀원 A | 학습 데이터의 클래스 불균형 | 장기 과제 |
| | 같은 알약 조합인데 촬영 각도만 다른 이미지 존재 | 팀원 C에게 인계 |
| | 등장이 적은 희귀 알약이 각도만 다른 이미지에만 존재 | 장기 과제(train/val 분할 문제) |
| | 알약끼리 너무 가까워 바운딩 박스가 겹친 데이터 | 해결 |
| | 빈 공간에 바운딩 박스가 쳐진 데이터 | 해결 |
| 팀원 B | JSON 파일의 결측치(NaN)가 18개 이미지에서 공통으로 발견됨 | 결측치 중심으로 EDA 계속 진행 |
| 팀원 C | 완전히 겹친 바운딩 박스 3장 발견 | 해결, 팀원 A의 각도 이슈 인계 |
| 팀원 D | 알약을 다 담지 못하고 잘린 바운딩 박스 발견 | 해결, 넉넉한 박스 처리 방법 조사 |

### 결측치 개수의 불일치

팀원 B는 JSON 파일의 결측치를 살펴보던 중 18개 이미지에서 결측치가 무더기로 발견되는 것을 확인했다. 지금까지 팀에 공유된 바운딩 박스 누락 개수는 16개였다. 그래서 실제 누락이 18개일 가능성을 의심해볼 실마리가 되었다. 1일차 마무리 회의에서 나온 "바운딩 박스를 수정하기 전에 NaN의 의미와 원인을 먼저 확인하자"는 피드백이 이어진 작업이기도 했다.

### 바운딩 박스 면적 불일치

팀원 D는 알약을 전부 담지 못하고 잘린 바운딩 박스를 발견해 수정했다. 그 과정에서 반대로 알약보다 넉넉하게 쳐진 박스도 확인했다. 넉넉한 박스는 IoU를 실제보다 높게 만들 수 있어, 이런 경우를 어떻게 처리할지 조사하기로 했다. 면적 불일치를 해결한 뒤에는 원래 다른 라벨이었던 박스가 같은 라벨로 바뀌었는지도 확인하기로 했다.

## 4. 핵심 논의: 각도만 다른 이미지는 같은 데이터인가

마무리 회의에서 가장 오래 논의한 주제는 팀원 A가 제기한 각도 이슈였다.

### 문제 상황

같은 알약 조합(예: A, B, C 알약이 한 사진에 함께 있는 경우)을 카메라 각도만 70도, 75도, 90도로 바꿔 촬영한 이미지가 여러 장 존재했다. 문제는 등장 횟수가 적은 희귀 알약이 이런 이미지에만 포함되어 있다는 점이었다.

### 사실상 같은 데이터라는 의견

팀원 A는 해당 이미지들이 처음 촬영될 때 카메라의 각도만 다를 뿐이므로 사실상 같은 데이터라고 설명했다. 그리고 이 데이터에 어떻게 대응할지가 중요하다고 강조했다.

팀원 B도 사람의 눈으로 보면 사실상 같은 사진이라고 보았다. 배열이 달라 보이는 사진도 180도 회전하면 똑같아진다는 의견이었다. 따라서 비슷한 사진을 세 장이나 남기기보다 한 장만 남기고 증강을 적용하는 편이 더 간편하다고 제안했다.

### 같은 데이터인지 먼저 확인하자는 의견

팀장은 해당 이미지들이 정말 같은 데이터인지 먼저 확인해야 한다고 주장했다. 각 알약의 클래스 구성은 같지만 배열이 다르기 때문에, 모델이 읽을 때는 사실상 다른 데이터일 수 있다는 피드백이었다.

### 검증 누수와의 연결

이 논의는 중복 이미지를 삭제할지 말지의 문제에 그치지 않았다. train과 validation을 어떻게 나눌지와 직접 연결되는 문제였다.

사실상 같은 장면이 train과 validation에 나뉘어 들어가면, 모델은 학습 중에 본 것과 거의 같은 이미지로 검증을 받게 된다. 이 경우 검증 성능이 실제 일반화 성능보다 높게 나타날 수 있다. 특히 희귀 클래스가 각도만 다른 이미지에 집중되어 있었기 때문에, 이미지 수만 보고 무작위로 분할하면 희귀 클래스에 대한 검증 결과를 신뢰하기 어려워질 수 있었다.

### 논의 결과

이 쟁점에 대한 의견은 다른 팀원들 사이에서도 갈렸다. 그래서 2일차에는 결론을 확정하지 않았다. 대신 해당 이미지를 같은 데이터로 볼지, 다른 데이터로 볼지 판단할 근거를 팀원 A가 조사하기로 했다. 회전하면 같은 사진이 된다는 팀원 B의 의견도 판단 기준에 포함해 확인하기로 했다.

## 5. 팀 관점의 회고

2일차에는 작업 관리 방식을 바꾸면서 EDA 결과를 공유하는 흐름이 달라졌다. 발견한 문제를 이슈 단위로 정리하고 해결, 인계, 장기 과제로 나누면서, 누가 무엇을 하는지뿐 아니라 데이터에 어떤 문제가 있는지가 팀 전체에 드러났다. 다만 도구를 도입하는 과정에서 설명과 설정 지원에 많은 시간이 들었다. 1일차에 확인한 것처럼, 반복되는 질문은 공통 안내로 정리해 둘 필요가 있다.

데이터 측면에서는 클래스 불균형뿐 아니라 유사하게 촬영된 이미지가 train과 validation에 나뉘는 문제를 고려해야 한다는 점을 확인했다. 사람 눈에 같아 보이는 이미지와 모델 입장에서 같은 이미지가 같은지는 직접 확인하기 전까지 단정할 수 없었다.

팀장 관점에서는 서로 다른 해석이 나왔을 때 바로 결론을 내리기보다, 무엇을 확인하면 판단할 수 있는지 공통 기준을 정하는 것이 중요한 역할이었다. 다만 "같은 데이터"에 대한 정의가 팀원마다 달랐던 만큼, 판단 기준의 초안이라도 함께 정리해 두었다면 다음 논의가 더 수월했을 것이다.
