프로젝트 첫날에는 알약 인식 기반 복용 기록 서비스의 문제를 정의하고, 팀 개발 환경과 협업 기반을 마련했다. 오전에는 서비스의 핵심 사용자 경험을 논의했고, 오후에는 환경 설정 문제를 해결한 뒤 EDA를 진행했다. 마무리 회의에서는 데이터 보완 결과와 접근 방법에 대한 피드백을 공유했다.

## 1. 주요 일정

| 시간 | 활동 |
| --- | --- |
| OT 이후 오전 10시~11시 | 문제 정의 및 서비스 방향 토론 |
| 오전 토론 이후~오후 3시 | GitHub 레포지토리 구성, 개발 환경 설정 및 문제 해결 |
| 오후 3시 이후 | EDA 및 데이터 품질 확인 |
| 오후 6시경 | 작업 결과 공유 및 피드백 |

## 2. 문제 정의: 복용 여부를 기억하고 기록하는 부담 줄이기

팀은 여러 종류의 약을 복용하는 사용자가 **오늘 어떤 약을 먹었는지 기억하고 기록하는 데 겪는 어려움**에 주목했다. 복용 시간과 수량을 관리해야 하는 상황에서 기록이 번거롭거나 기억이 불확실하면 중복 복용이나 미복용으로 이어질 우려가 있다는 문제의식이었다.

여러 제안 가운데 소희님과 다른 팀원이 제출한 내용을 중심으로, 약 사진을 촬영하면 해당 시각을 기준으로 복용 기록을 자동으로 남기는 서비스를 논의했다. 사용자가 복용 내역을 일일이 외우거나 직접 입력하는 부담을 줄이는 것이 목적이다.

사전 멘토링 자료를 바탕으로 작성한 README용 문제 정의 초안도 공유했다. 이를 팀의 서비스 방향으로 정리하면 다음과 같다.

> 여러 종류의 약을 복용하는 사용자는 약마다 정해진 복용 시간과 수량을 관리해야 한다. 우리 팀은 알약 객체 탐지 모델과 앱을 연결하여 복용 기록을 남기는 부담을 줄이고, 사용자가 자신의 복용 내역을 쉽게 확인할 수 있도록 돕고자 한다.

모델의 기본 입출력은 다음과 같이 정리했다.

| 구분 | 내용 |
| --- | --- |
| 모델 입력 | 알약 이미지 |
| 학습용 정답 데이터 | 바운딩 박스(bbox)와 클래스 라벨 |
| 모델 출력 | 예측 바운딩 박스, 신뢰도 점수, 클래스 이름 |

다만 사진은 촬영 시점의 약을 보여주는 자료이므로, **촬영 기록과 실제 복용 여부를 어떻게 연결할지는 별도의 설계 과제**로 남았다.

## 3. 핵심 논의: 약통 촬영과 알약 촬영

서비스 방향을 구체화하는 과정에서 가장 큰 쟁점은 **사용자가 약통을 촬영하도록 할 것인지, 복용할 알약을 직접 촬영하도록 할 것인지**였다.

### 약통 촬영: 사용자의 기록 부담 최소화

약통 촬영을 제안한 측에서는 편의성을 강조했다. 복용할 알약을 손바닥이나 바닥에 펼쳐 촬영하는 것보다 약통을 촬영하고 알림을 받는 방식이 간편하다는 의견이었다.

특히 복용하는 약의 종류와 수량이 많은 사용자는 알약을 한곳에 모아 한 장의 사진으로 촬영하는 과정 자체가 부담이 될 수 있다는 사례가 공유되었다. 팀은 이를 통해 촬영 과정의 번거로움이 서비스 사용을 어렵게 만들 수 있다는 점을 고려하게 되었다.

### 알약 촬영: 복용 준비 과정과 기록 연결

알약 촬영을 지지한 측에서는 실제로 복용할 약을 꺼내고 준비하는 과정에 주목했다. 약통을 촬영하거나 알림을 확인하는 것보다, 알약을 직접 꺼내 촬영하는 행동이 복용 과정과 더 밀접하게 연결될 수 있다는 의견이었다.

약을 다른 용기에 옮겨 담거나 약통을 분실하는 상황도 고려해야 한다는 주장이 나왔다. 국내외의 약 포장·보관 방식 차이에 관한 의견도 있었으며, 이는 향후 대상 사용자의 실제 복용 환경을 조사하며 확인할 필요가 있다.

### 논의 결과

1일차에는 **알약 촬영을 중심으로 프로젝트를 진행하는 방향**을 잡았다. 다만 모든 팀원이 충분히 납득한 최종 합의에 도달한 것은 아니었다.

사용자의 촬영 부담을 얼마나 줄일 수 있는지, 촬영이 복용 행동을 돕는지, 기록을 어느 수준까지 신뢰할 수 있는지는 계속 검토하기로 했다.

## 4. 개발 환경과 협업 기반 구축

### GitHub 레포지토리 및 공통 환경 구성

팀은 `uv`를 활용해 버전을 맞추고 가상환경을 구성하기로 했다. 프로젝트 구조는 기존 알약 탐지 프로젝트를 참고했다.

팀장 동욱님은 레포지토리와 공통 개발 환경을 구성하는 한편, 팀원들의 환경 설정 문제와 협업 방식에 관한 질문에 대응했다. 팀장을 제외한 팀원 모두 관련 경험이 부족했기 때문에, 첫날에는 작업을 시작할 수 있는 기반을 마련하는 데 많은 시간이 필요했다.

### 환경 설정 중 발생한 문제

대표적인 문제는 사전에 정한 가상환경과 실제 실행 커널이 달라진 사례였다. 데이터 로드 과정에서 AI가 제안한 라이브러리와 커널을 사용하면서, 기존에 설정한 환경 대신 `.venv`가 포함된 다른 커널을 선택했고 환경 불일치가 발생했다.

이 사례의 핵심은 특정 커널 이름 자체가 아니라, **팀에서 정한 환경과 현재 실행 환경이 같은지 확인하지 않은 채 설정을 변경한 것**이었다.

팀은 이 경험을 통해 다음 사항의 중요성을 확인했다.

- README에 정리한 공통 환경 설정을 우선 확인한다.
- 라이브러리를 설치하는 환경과 코드를 실행하는 커널이 일치하는지 점검한다.
- AI가 제안한 설정이나 명령이 현재 프로젝트에 적합한지 검토한다.

상세한 오류와 해결 과정은 환경 설정 트러블슈팅 페이지에 별도로 기록했다.

### 작업 관리 도구 검토

이슈와 할 일은 칸반보드 형태로 관리하는 방식을 검토했다. 처음에는 Notion을 사용하려 했지만, GitHub Projects도 선택지로 확인하면서 두 도구를 비교하게 되었다.

첫날에는 도구를 확정하지 않았으며, **작업 관리 도구 선택은 2일차로 넘겼다.**

## 5. EDA와 데이터 품질 점검

오후 3시 이후에는 환경 설정을 마친 팀원들이 EDA를 진행했다. 주요 작업은 데이터 구조 확인, 바운딩 박스 누락 및 이상치 탐색, 라벨 오류 보완이었다.

| 담당 | 주요 작업 |
| --- | --- |
| 바운딩 박스 보완을 진행한 팀원 | 일부 알약의 바운딩 박스 누락 확인, 추가 및 검증 |
| 영훈님 | 데이터 로드 및 기본적인 EDA |
| 재민님 | 바운딩 박스 크기 이상치 탐색과 라벨 오류 수정 |

### 일부 알약의 바운딩 박스 누락

학습 이미지에서 바운딩 박스가 누락된 사례를 확인했다. 실제 이미지를 살펴본 결과, 이미지 전체에 라벨이 없는 것이 아니라 **한 이미지에 포함된 알약 4개 중 일부에만 박스가 없는 형태**였다.

해당 이미지를 삭제하면 정상적으로 라벨링된 알약 정보도 함께 제외된다. 담당 팀원은 삭제 시 기존 정답 박스 16개가 함께 사라질 것으로 판단하여, 이미지를 삭제하는 대신 누락된 박스를 추가하고 검증했다. 보완 과정에는 OpenCV를 활용했다.

이 작업은 누락 데이터를 일괄 삭제하기 전에 실제 이미지와 라벨 상태를 확인했다는 점에서 의미가 있었다. 다만 수정 기준과 검증 방법을 명확히 설명할 수 있도록 정리할 필요도 확인했다.

### 바운딩 박스 크기 이상치

재민님은 바운딩 박스의 크기를 살펴보는 과정에서 사분위 기준으로 이상치에 해당하는 사례를 발견했다. 실제 이미지를 확인한 결과, 알약 자체가 커서 박스 크기도 크게 나타난 경우였다.

이를 통해 팀은 **통계적 이상치가 반드시 데이터 오류를 의미하지는 않으며, 실제 이미지와 함께 판단해야 한다**는 점을 확인했다.

### 라벨 오류 수정

재민님은 라벨 오류 한 건을 발견해 기존 바운딩 박스를 제거하고 새로운 박스로 교체했다.

결과 공유 과정에서는 오류의 원인과 수정 근거를 충분히 이해한 뒤 AI를 활용할 필요가 있다는 피드백이 나왔다. 수정 결과를 만드는 것과 함께, 왜 해당 수정이 필요한지 설명할 수 있어야 한다는 취지였다.

## 6. 마무리 회의와 팀 피드백

오후 6시경 마무리 회의에서는 EDA 결과와 데이터 보완 과정을 공유했다.

팀장 동욱님은 바운딩 박스 수정에 바로 접근하기 전에, **데이터셋 피처에 나타나는 `NaN` 값의 의미와 원인을 먼저 살펴보았으면 좋았겠다**는 피드백을 전달했다.

또한 OpenCV를 사용해 바운딩 박스를 보완한 팀원들에게, 사용한 기능과 동작 방식을 충분히 이해할 필요가 있다고 강조했다. 팀은 이 피드백을 수용하고, AI와 라이브러리를 활용하더라도 다음 내용을 스스로 확인할 수 있어야 한다는 점을 공유했다.

- 어떤 문제가 발생했는가?
- 왜 수정이 필요한가?
- 사용한 도구는 어떤 역할을 하는가?
- 수정 결과가 타당한지는 어떻게 검증했는가?

## 7. 팀 관점의 회고

첫날에는 예상보다 많은 시간을 환경 설정과 협업 안내에 사용했다. 공통 개발 환경을 정하는 것만으로는 충분하지 않았고, 팀원 모두가 같은 기준을 이해하고 실제 작업에 적용할 수 있도록 돕는 과정이 필요했다.

서비스 논의에서는 **사용자 편의성과 복용 기록의 신뢰성을 함께 고려해야 한다**는 점을 확인했다. 알약 촬영이라는 기능을 구현하는 것에 앞서, 사용자가 매일 이 과정을 감당할 수 있는지 검토해야 한다.

데이터 작업에서는 실제 이미지를 확인하며 누락과 이상치를 구분한 점이 의미 있었다. 동시에 데이터 보완에 앞서 원인을 파악하고, 수정 근거와 검증 과정을 기록하는 습관이 필요하다는 점도 배웠다.

팀장 관점에서도 프로젝트 관리는 일정과 할 일을 배분하는 것에 그치지 않았다. 첫날에는 팀원들의 진행을 막는 문제를 해결하고, 공통 환경과 협업 방식을 이해하도록 지원하는 일이 중요한 역할이었다.
